# AI小说转剧本工具 - 项目整体设计文档

## 1. 项目背景与目标

### 1.1 项目背景

在影视工业化进程中，将文学作品（小说）改编为影视剧本是一个耗时耗力的环节。编剧需要反复阅读原著、提炼关键场景与对白、重构叙事结构，尤其是长篇小说动辄数十万字，人工改编周期往往以月甚至年计。随着大语言模型（LLM）能力的快速提升，AI 已能在理解叙事结构、提取人物对话、生成格式化脚本等方面提供实质性辅助，大幅压缩改编周期。

### 1.2 项目目标

构建一个**AI驱动的小说转剧本SaaS工具**，核心目标如下：

- **自动化转换**：用户上传小说文件（.txt / .md，UTF-8编码），系统自动解析章节，调用 LLM 将小说内容转换为结构化的剧本格式（YAML）。
- **多模式支持**：支持**电影剧本**、**电视剧剧本**、**微短剧剧本**三种输出模式，适配不同叙事节奏与篇幅要求。
- **长文本处理**：针对百万字级长篇小说，实现智能分段、上下文摘要传递、异步任务调度，突破 LLM Token 窗口限制。
- **在线编辑与预览**：提供剧本在线预览与编辑能力，用户可对 AI 生成结果进行人工修正并导出。
- **项目管理**：支持多项目、多版本的历史记录管理，方便用户迭代优化。

### 层间交互说明

| 交互方向 | 协议/方式 | 用途 |
|---------|----------|------|
| 前端 → 后端 | HTTP REST (JSON) | 登录注册、文件上传、项目CRUD、剧本编辑等同步请求 |
| 后端 → 前端 | WebSocket | 剧本转换进度实时推送 |
| 后端 → Celery | Redis (Broker) | 投递异步转换任务 |
| Celery → 后端 | Redis (Backend) | 任务结果存储与查询 |
| 后端 → PostgreSQL | SQL (asyncpg/SQLAlchemy) | 用户数据、项目数据、剧本数据持久化 |
| 后端 → MinIO | S3 兼容 API | 上传小说文件、存储导出的剧本文件 |
| 后端/Celery → LLM | HTTPS (OpenAI 兼容 API) | 调用 DeepSeek API 进行文本转换 |

## 3. 技术栈选型及理由

### 3.1 前端：Vite + Vue 3

| 技术 | 版本建议 | 选型理由 |
|------|---------|---------|
| **Vite** | 6.x | 极快的冷启动与 HMR（热模块替换），原生 ESM 支持，构建速度远优于 Webpack |
| **Vue 3** | 3.5+ | Composition API 提供更好的逻辑复用与 TypeScript 支持；生态成熟，社区活跃 |
| **Pinia** | 2.x | Vue 官方推荐的状态管理库，API 简洁，DevTools 支持完善 |
| **Element Plus** | 2.x | 企业级 Vue 3 组件库，提供文件上传、表单、表格等开箱即用组件 |
| **CodeMirror 6** | 6.x | 用于剧本 YAML 在线编辑，支持语法高亮、自动补全、错误提示 |
| **Vue Router** | 4.x | SPA 路由管理 |

### 3.2 后端：FastAPI + Celery

| 技术 | 版本建议 | 选型理由 |
|------|---------|---------|
| **FastAPI** | 0.115+ | 异步原生支持（asyncio），自动生成 OpenAPI 文档，类型安全，性能接近 Node.js/Go |
| **Uvicorn** | 0.34+ | 高性能 ASGI 服务器，支持多 worker 部署 |
| **Celery** | 5.4+ | Python 生态最成熟的分布式任务队列，支持任务重试、优先级、定时任务 |
| **SQLAlchemy 2.0** | 2.0+ | 异步 ORM 支持（asyncpg driver），声明式模型定义，迁移工具 Alembic |
| **Pydantic** | 2.x | 请求/响应数据校验，与 FastAPI 深度集成 |
| **python-multipart** | - | 文件上传解析 |

**为什么选 Celery 而不是 ARQ / Dramatiq？**
- Celery 社区最大，文档最全，与 FastAPI 集成方案成熟。
- Redis 作为 Broker 即可满足本项目规模需求，无需引入 RabbitMQ。
- 支持任务组（group）、链式任务（chain）、和弦（chord），适合章节并发转换后合并的场景。

### 3.3 数据库：PostgreSQL

| 选型理由 |
|---------|
| 支持 JSON/JSONB 类型，适合存储剧本结构化数据（YAML → JSON） |
| ACID 事务保障，确保项目数据的强一致性 |
| 丰富的高级功能：全文检索（用户搜索历史项目）、窗口函数（统计报表） |
| 异步驱动 asyncpg 性能卓越，与 SQLAlchemy 2.0 无缝集成 |

### 3.4 缓存 / 消息队列：Redis

| 角色 | 用途 |
|------|------|
| **Celery Broker** | 消息中间件，传递异步任务 |
| **Celery Backend** | 存储任务执行结果 |
| **缓存层** | 缓存用户 Session（JWT Token 黑名单）、热点数据（剧本模板、模型列表） |
| **WebSocket 状态** | 配合 FastAPI WebSocket，管理连接状态与频道订阅 |

### 3.5 对象存储：MinIO

| 选型理由 |
|---------|
| 完全兼容 AWS S3 API，代码迁移至云存储零成本 |
| 部署简单（Docker 单容器即可），资源占用低 |
| 支持文件版本管理，适合剧本多次导出的场景 |
| **开发环境降级方案**：本地文件系统（`/data/uploads`），通过策略模式抽象存储接口，一行配置切换 |

### 3.6 LLM：DeepSeek API

| 模型 | 适用场景 | 理由 |
|------|---------|------|
| **deepseek-chat** (DeepSeek-V3) | 日常剧本转换的主力模型 | 上下文 128K Token，性价比极高，适合逐章转换的批量调用 |
| **deepseek-r1-0528** (DeepSeek-R1) | 复杂情节、关键高潮场景的高质量改写 | 推理能力强，适合需要深度叙事结构调整的场景，作为可选项提供给用户 |

**API 调用策略**：
- 使用 OpenAI 兼容接口，代码无需额外适配（`openai` Python SDK 直连）。
- 实现**Token 预算管理**：每章节输入控制在模型上下文的 60% 以内，预留 40% 给输出与系统提示。
- 支持**指数退避重试**，应对 API 限流（429 状态码）。

### 4.2 模块详解

#### 4.2.1 用户管理

- **注册/登录**：JWT 认证（Access Token + Refresh Token）
- **Token 管理**：Redis 黑名单实现登出失效
- **用户配额**：每日/每月转换字数限制（可配置）

#### 4.2.2 小说上传与章节解析

- **文件格式**：支持 `.txt`、`.md`（UTF-8 编码），单文件上限 50 万字（UTF-8 编码下文件大小约 1.5 MB）
- **章节识别**：正则匹配常见章节标题模式（如 "第X章"、"Chapter X"、"卷一" 等）
- **解析流程**：
  1. 文件上传至 MinIO / 本地存储
  2. 后台异步解析章节边界，存储于 PostgreSQL（`chapters` 表）
  3. 用户可手动调整章节划分（合并、拆分、重命名）

#### 4.2.3 剧本类型选择

用户在创建转换项目时选择输出模式：

| 模式 | 典型字数 | 剧本页数 | 结构特征 |
|------|---------|---------|---------|
| **电影剧本** | 30,000-50,000字 | 90-120页 | 三幕结构，单一主线，场景连续 |
| **电视剧剧本** | 200,000-500,000字 | 30-40集 | 多线叙事，集/幕粒度，每集独立高潮 |
| **微短剧剧本** | 3,000-10,000字/集 | 1-3分钟/集 | 快节奏，强反转，每集一个钩子 |

不同模式对应不同的**System Prompt**和**输出 Schema**。

#### 4.2.4 AI 转换引擎（核心模块）

```
小说文本 ──▶ 预处理 ──▶ 章节分片 ──▶ LLM 调用 ──▶ 结果合并 ──▶ 格式校验 ──▶ 剧本输出
              │                      ▲
              │         上下文摘要    │
              └──────────────────────┘
```

- **预处理**：清洗文本（去除无关空白、广告）、角色名识别
- **章节分片**：按 Token 计算器分片，确保每片在模型窗口内
- **上下文传递**：上一章节的摘要 + 关键角色状态 → 作为下一章节的 System Prompt 上下文
- **结果合并**：Celery Chord 机制，所有章节转换完成后触发合并任务
- **格式校验**：输出必须严格符合预设的 YAML Schema，不合规则自动重试或标记人工处理

#### 4.2.5 进度跟踪

- **WebSocket 实时推送**：任务状态变更时通过 WebSocket 广播进度百分比
- **进度粒度**：
  - 10% - 文件上传完成
  - 20% - 章节解析完成
  - 30%-90% - 各章节转换中（按章节数均分）
  - 95% - 结果合并中
  - 100% - 剧本生成完毕

#### 4.2.6 剧本预览与在线编辑

- **预览**：YAML 渲染为可读的剧本格式（角色-对白-场景卡片）
- **在线编辑**：CodeMirror 6 编辑器，YAML 语法高亮 + Schema 校验
- **版本管理**：每次保存生成新版本，支持版本对比与回滚

#### 4.2.7 历史项目管理

- **项目列表**：按创建时间/更新时间排序，支持搜索
- **项目状态**：草稿/转换中/已完成/失败
- **操作**：查看、编辑、重新转换、删除、导出（YAML / PDF）

## 5. 长篇小说处理策略

长篇小说（百万字级）的核心挑战在于 LLM 上下文窗口有限，无法一次性处理全部内容。本方案采用以下策略组合：

### 5.1 章节自动分段

```
全本小说 ──▶ 正则识别章节 ──▶ [第1章] [第2章] [第3章] ... [第N章]
                                        │
                          ┌─────────────┼─────────────┐
                          ▼             ▼             ▼
                      Token计数      Token计数      Token计数
                          │             │             │
                     ≤ 60K?    ≤ 60K?      ≤ 60K?
                      Y/N          Y/N          Y/N
```

- 单章 Token 数 ≤ 60K（约 4.5 万汉字）：**直接送入 LLM**
- 单章 Token 数 > 60K：**按段落边界递归二分切割**，每个子片段独立转换后合并

### 5.2 上下文摘要传递（Context Summarization）

长篇叙事的核心难题是**跨章节一致性**——角色关系、前文伏笔需在整个转换过程中保持连贯。

```
┌──────────┐     ┌──────────┐     ┌──────────┐     ┌──────────┐
│  第1章    │ ──▶ │  第2章    │ ──▶ │  第3章    │ ──▶ │  ...     │
│  LLM转换  │     │  LLM转换  │     │  LLM转换  │     │          │
└────┬─────┘     └────┬─────┘     └────┬─────┘     └──────────┘
     │                │                │
     ▼                ▼                ▼
┌──────────┐     ┌──────────┐     ┌──────────┐
│ 摘要生成  │ ──▶ │ 摘要生成  │ ──▶ │ 摘要生成  │
│ (角色状态  │    │ (角色状态  │    │ (角色状态  │
│  关键情节) │    │  关键情节) │    │  关键情节) │
└──────────┘     └──────────┘     └──────────┘
```

**关键实现细节**：
- 每次章节转换完成后，追加一次**轻量 LLM 调用**生成摘要（仅提取：角色状态变化、关键情节节点、未解伏笔）
- 摘要内容约 500-1000 Token，作为下一章节 System Prompt 的 `context_summary` 字段注入
- 摘要**累积传递**：第 N 章的上下文包含前 N-1 章的累积摘要

### 5.3 Celery 异步任务与 WebSocket 进度反馈

```
用户点击"开始转换"
        │
        ▼
┌─────────────────┐
│ FastAPI 接收请求 │ ──▶ 创建 Project（状态: converting）
└────────┬────────┘
         │
         ▼
┌─────────────────┐     Redis Broker      ┌──────────────────┐
│  投递 Celery    │ ──────────────────▶   │  Celery Worker   │
│  Chord 任务     │                       │  逐章调用 LLM     │
└────────┬────────┘                       └────────┬─────────┘
         │                                         │
         │    WebSocket ◀──────────────────────────┘
         │    (进度: 35%)
         ▼
┌─────────────────┐
│  Chord 回调      │ ──▶ 合并所有章节 ──▶ 校验 YAML Schema
│  (merge_scripts) │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  Project 状态    │
│  → completed    │ ──▶ WebSocket 推送 (进度: 100%)
└─────────────────┘
```

**Celery Chord 机制**：
```python
# 伪代码示意
chapters = [chapter_1, chapter_2, ..., chapter_n]
header_tasks = [convert_chapter.s(ch) for ch in chapters]
callback_task = merge_scripts.s(project_id=project_id, script_type=script_type)

# header 中的任务可并发执行，全部完成后自动调用 callback
chord(header_tasks)(callback_task)
```

**WebSocket 进度反馈流程**：
1. FastAPI WebSocket endpoint 接收连接，按 `user_id` + `project_id` 建立频道
2. Celery Worker 中每个章节任务完成后，通过 Redis Pub/Sub 或直接调用 FastAPI 内部接口更新进度
3. FastAPI 将进度推送给对应频道的 WebSocket 客户端

### 5.4 Token 窗口管理

| 参数 | 值 | 说明 |
|------|---|------|
| 模型上下文上限 | 128K Token | deepseek-chat 原生支持 |
| 单段输入上限 | 60K Token (~4.5万汉字) | 保留约 50% 给输出 + system prompt |
| System Prompt | ~2K Token | 剧本格式指令 + Schema 描述 |
| 上下文摘要 | ~1K Token | 前文章节累积摘要 |
| 输出预留 | ~65K Token | 足够生成完整剧本段落 |

**超长章节处理**：若单章超过 60K Token，按段落边界递归切割为多个子片段，每个子片段独立调用 LLM，结果由 `merge_scripts` 任务按序拼接。

## 6. 剧本输出格式 (YAML Schema)

### 6.1 通用剧本结构

```yaml
schema_version: "1.0"

# 剧本元信息
meta:
  title: "剧本标题"
  source_novel: "原著小说名"
  author: "原作者"
  script_type: "movie"          # movie | tv_series | mini_series
  created_at: "2026-06-05T10:00:00Z"
  version: 1

# 角色列表
characters:
  - id: "char_001"
    name: "张三"
    aliases: ["三哥"]
    gender: "男"
    age: 28
    role: "protagonist"         # protagonist | antagonist | supporting
    description: "一名退役特种兵，性格沉稳内敛..."
    first_appearance: "scene_001"

# 剧本正文
script:
  # ===== 电影模式 =====
  # movie 模式：三幕结构
  acts:
    - act: 1
      title: "建置"
      scenes:
        - scene_id: "scene_001"
          location: "张三的公寓 - 客厅 - 日"
          characters_present: ["char_001"]
          content:
            - type: "action"
              text: "张三坐在昏暗的客厅里，手中摩挲着一枚褪色的军徽。窗外城市的霓虹灯光映在他疲惫的脸上。"
            - type: "dialogue"
              character: "char_001"
              text: "三年了，还是逃不掉。"

  # ===== 电视剧模式 =====
  # tv_series 模式：集-幕-场
  episodes:
    - episode: 1
      title: "归来"
      acts:
        - act: 1
          scenes:
            - scene_id: "ep1_scene_001"
              location: "..."
              characters_present: ["..."]
              content:
                - type: "action"
                  text: "..."
                - type: "dialogue"
                  character: "char_001"
                  text: "..."

  # ===== 微短剧模式 =====
  # mini_series 模式：集-场（无幕），强调钩子
  episodes:
    - episode: 1
      title: "深夜来电"
      hook: "一个神秘电话，打破了十年的平静。"  # 微短剧特有：每集悬念钩子
      scenes:
        - scene_id: "ep1_scene_001"
          location: "..."
          duration_seconds: 45         # 微短剧特有：场景时长
          characters_present: ["..."]
          content:
            - type: "dialogue"
              character: "char_001"
              text: "..."
```

### 6.2 三种模式的 Schema 差异

| 字段 | 电影 (movie) | 电视剧 (tv_series) | 微短剧 (mini_series) |
|------|:-----------:|:---------------:|:-----------------:|
| 顶层结构 | `acts` | `episodes` → `acts` | `episodes` |
| `hook` 字段 | 无 | 无 | **必填**（每集） |
| `duration_seconds` | 无 | 无 | **必填**（每场） |
| Scene 数量 | 60-120 场 | 30-40 集 × 10-15 场 | 数集 × 5-8 场 |

### 6.3 YAML Schema 校验

使用 Python `jsonschema` 库对 LLM 输出进行结构化校验：

- 必要字段完整性检查（`meta.script_type`、`characters[].id` 等）
- 枚举值合法性（`script_type` ∈ {movie, tv_series, mini_series}）
- 引用完整性（`dialogue.character` 必须存在于 `characters[].id`）

**校验失败处理**：
1. 自动重试（最多 3 次），每次重试将校验错误信息注入 Prompt
2. 3 次重试后仍失败 → 标记该章节为 `needs_manual_review`，通知用户人工处理

## 7. 部署与运维考虑

### 7.1 Docker Compose 容器化

```yaml
# docker-compose.yml 结构示意
services:
  frontend:        # Vue 3 + Nginx（生产）或 Vite dev server（开发）
  backend:         # FastAPI + Uvicorn
  celery_worker:   # Celery Worker
  celery_beat:     # Celery Beat（定时任务：清理过期文件等）
  postgres:        # PostgreSQL 16
  redis:           # Redis 7
  minio:           # MinIO（或开发环境禁用，回退本地存储）
```

**容器规划**：

| 服务 | 镜像 | 端口 | 资源建议 |
|------|------|------|---------|
| frontend | node:22-alpine / nginx:alpine | 80 / 5173 (dev) | 512MB RAM |
| backend | python:3.12-slim | 8000 | 1GB RAM |
| celery_worker | python:3.12-slim | - | 512MB RAM × N worker |
| postgres | postgres:16-alpine | 5432 | 1GB RAM |
| redis | redis:7-alpine | 6379 | 256MB RAM |
| minio | minio/minio:latest | 9000, 9001 | 512MB RAM |

### 7.2 数据持久化

```
volumes/
├── postgres_data/     # PostgreSQL 数据文件
├── redis_data/        # Redis RDB/AOF 持久化
├── minio_data/        # MinIO 对象存储
└── uploads/           # 开发环境本地文件存储
```

- **PostgreSQL**：使用 Docker Volume 挂载 `/var/lib/postgresql/data`，定期 `pg_dump` 备份
- **MinIO**：挂载 `/data` 目录，开发环境可禁用 MinIO，后端自动降级为本地文件系统（`app/core/storage.py` 中策略模式切换）
- **Redis**：开启 AOF 持久化，防止任务丢失

### 7.3 环境配置管理

- 使用 `.env` 文件管理环境变量（数据库连接串、API Key 等）
- Docker Compose 通过 `env_file` 注入
- 敏感信息（DeepSeek API Key、JWT Secret）严禁硬编码

### 7.4 运维建议

| 方面 | 方案 |
|------|------|
| **日志收集** | Celery 与 FastAPI 统一输出 JSON 格式日志，可由 ELK/Loki 收集 |
| **健康检查** | 各服务提供 `/health` 端点，Docker Compose `healthcheck` 指令监控 |
| **限流保护** | FastAPI 中间件实现 IP 级别速率限制；LLM API 调用实现并发控制（Semaphore） |
| **优雅关闭** | Celery Worker 配置 `task_acks_late=True`，避免任务中断丢失 |
| **水平扩展** | Celery Worker 可按需增加副本（`docker-compose up --scale celery_worker=3`） |
